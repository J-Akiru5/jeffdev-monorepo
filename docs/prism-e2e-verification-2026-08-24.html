The whole chain, proven or broken — E2E verification report

docs/prism-e2e-verification-2026-08-24.html · branch feat/prism-pass · KWADRA TBI demo Wednesday Aug 26

Summary. Two halves of Prism — the rule-engine Pass and the setup pipeline (prism init / pull / ide-setup) — had never been run together on a project Prism had never seen. We ran the complete chain twice on genuinely clean Next.js 16 + Tailwind 4 scaffolds outside the monorepo, before and after fixes. Before fixes: the mechanics all worked (init on a project with no .claude/, token extraction, hook wiring), but the product was a no-op — generated rules shipped at warn severity while hook mode only ever surfaces block, so an agent wrote eight-plus violations across both runs and the Pass said nothing, exit 0, every time. A second latent defect surfaced alongside: the generated token rule flagged the tokens' own definitions inside globals.css. After two approved, surgical fixes (token rule ships block; scoped to code files only) and zero engine/hook/schema changes, the full chain works unattended: Claude Code's own transcript reports the Pass intercepting its writes and forcing design-token compliance, final files contain zero raw hex, and the self-flagging is gone. 06The consult & approved fixes

Per session ground rules, everything touching generated rule shape stopped for approval. Options presented: (A) token rule ships block, brackets stay warn; (B) surface warns non-blockingly — rejected on evidence, Claude Code never feeds exit-0 stderr to the model; (C) ship as-is and report a no-op product. For the self-flagging: (A) scope the generated rule to code files, or (B) leave it. Jeff approved A+A.

The fix lives entirely in src/init/generate-rules.ts — generation policy, not enforcement logic:

DIFF · src/init/generate-rules.ts (the entire behavioral change)
+/** Code-file extensions the generated required_token rule applies to.
+ *  Deliberately excludes .css/.scss: those hold the tokens' own definition
+ *  lines, which must never violate their own rule. */
+export const TOKEN_RULE_EXTENSIONS = [".tsx", ".jsx", ".ts", ".js", ".html"];

 rules.push({
   id: "styling/design-tokens",
   category: "styling",
-  severity: "warn",
+  severity: "block",
+  extensions: TOKEN_RULE_EXTENSIONS,
   instruction: "Use this project's own CSS variable tokens instead of these raw hex values…",
   check: { type: "required_token", tokenSet: "auto-detected-colors", tokenMap, … },
 });

Rationale, now encoded in the module docblock: token-map matches are exact hex literals lifted from the project's own source — true positives by construction, both runs produced zero false positives on code files, and a silent warn makes the Pass invisible to the agent. Bracket values are heuristic (they flag pristine scaffold code) so they stay advisory. No changes to engine.ts, parse.ts, format.ts, check.ts, or the v1 schema.

09Honest residual risks — read before Wednesday

  • Until 1.2.0 publishes to npm, the generated hook command cannot work from a cold install — npx resolves published 1.1.1, which has no check subcommand. For Wednesday's demo the package is installed from the local tarball, which mirrors the post-publish path exactly. Publish before anyone outside the repo tries this.
  • The PostToolUse hook fires after the write lands. The violating version of a file exists on disk momentarily; the agent then edits it into compliance within the same turn. That's Claude Code's PostToolUse contract, not a bug — but don't demo it as "pre-write blocking".
  • Arbitrary-bracket violations remain invisible to the agent by design. They show in prism check lint output only. If the demo wants them visible too, that's a deliberate promotion edit to the generated file — rehearse whichever way you choose.
  • A default create-next-app project yields only 4 thin tokens, and its own scaffold page.tsx carries bracket warnings. Extraction is honest, not magic: the enriched-project story ("seed your design system, get real rules") is the one to tell.
  • Dark-mode hex pairs map to the shared variable name (#0a0a0a → var(--background)) — semantically correct today; worth remembering if extraction ever grows per-theme awareness.
