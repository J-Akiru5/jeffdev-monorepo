The Pass could already enforce rules — it just had no way to get a rules.json onto a machine except by hand. This ships the two paths that fix that: prism init, which reads a project's own globals.css and Tailwind config and generates a working starter rule set with zero network calls and zero account, and prism pull, which fetches a team's rules from a new dashboard endpoint and fails safe on every error path — network, auth, or malformed response — so a bad pull can never break a working setup. Both write the exact same unchanged rules.json v1 shape. The dashboard is the upgrade, not the gate: a developer gets real enforcement from their own design system before they ever see a login screen.

01Inspection first — two things weren't what the brief assumed

Branch: staying on feat/prism-pass. It's already ahead of origin/develop by exactly the one commit this work depends on (the rule engine + v1 schema), working tree clean, nothing else in flight touches it. Target is still develop; this stacks rather than branching fresh.

Reading the existing rule engine and the dashboard's storage before writing anything surfaced two real forks that weren't visible from the task brief alone:

1. prism init already existed. It was a cloud-token MCP-wiring command for Cursor/Windsurf/VS Code/Claude Desktop — nothing like the local onboarding flow this task describes. Unpublished package, so the rename was safe: the old command moved to prism ide-setup.
2. The dashboard's rule storage doesn't match v1. prism_rules (Postgres/Supabase, migrated off Cosmos) uses category: performance|documentation|custom|… and severity: error|warning|info — not v1's four categories and two severities. And prism_brands, which holds real design tokens, has no relation to prism_projects at all — so server-side token-derived checks were off the table without a schema change, which was out of scope.

One thing was already solved: authenticate() in the dashboard's API layer already accepts an x-api-key header against a hashed lookup in prism_api_keys — exactly the "API key auth only" the brief asked for, reused as-is.

02Decisions made before writing code

Four choices were forks, not defaults, so they went to Jeff before any implementation: naming collision resolution, the token-extraction execution model, how prism pull identifies a project, and how the dashboard endpoint maps categories/severities that don't exist in v1.

prism init naming collision
→ Reclaim `init` for the local flow; old command becomes `prism ide-setup`.
Tailwind config extraction
→ Dynamic import for .js/.mjs/.cjs (accurate — same load path Tailwind itself uses); regex fallback for .ts (no TS runtime available) and as a safety net if the import throws.
How prism pull picks a project
→ Refined in the room: not a flat `projectSlug` string but `{ activeProject, projects: { [slug]: { id, lastPulled } } }` in `.prism/config.json` — additive, never assumes exactly one entry, so `prism projects use <slug>` / `prism projects list` can land later with zero config migration. Confirmed as fact, not assumption: API keys are user-scoped in `prism_api_keys` (no `project_id` column) — one key legitimately lists and fetches every project a user owns.
Dashboard category/severity mapping
→ error→block, warning/info→warn. performance/documentation/custom (the DB default) fold into architecture rather than being dropped — nothing a user authored in the dashboard silently vanishes on pull.

03prism init — the local path

Detection reads only the project's own files: package.json for Next.js/Tailwind and their versions, directory layout for app-vs-pages router. Token extraction has two tiers —

  • CSS custom properties from globals.css (checked across the common Next.js locations, app-root and src/-nested) — this covers Tailwind v4's CSS-first @theme{} tokens for free, since those are custom properties too. Hex-valued ones become a required_token rule; duplicate hex values keep their first-seen variable name.
  • Tailwind config colors — dynamically imported for .js/.mjs/.cjs (flattening nested palettes accurately, including spreads and computed keys a regex can't see), regex-extracted for .ts or if the import throws. These are informational only in the summary — with no CSS variable behind them there's nothing safe to enforce a swap to — but their presence still emits the arbitrary_value rule guarding the scale.

Every generated rule ships at severity: warn, never block — these come from regex heuristics against a codebase they've never been run on before, and a false positive shouldn't stop an agent's write on day one. Promoting a rule is a one-line edit.

Hook wiring merges .claude/settings.json: every existing key and matcher is preserved, a second run is a no-op (checks for an existing prism check --hook command before adding one), and malformed existing JSON is left untouched with a manual-fix snippet printed instead of being clobbered. Same discipline for .prism/rules.json itself — an existing file is never overwritten without --force or an explicit "yes" at the prompt; under --yes (the CI/demo flag) the safe default is to skip, not silently regenerate. The empty case (no tokens found at all) still writes valid JSON — a single advisory rule with no check field explaining what was searched and where to go next — rather than failing or emitting something JSON.parse can't read.

04prism pull — the synced path

Reads the API key from PRISM_API_KEY or .prism/config.json, resolves a project (via --project, the stored activeProject, or a prompt — first project as the Enter-through default, auto-picked under --yes), fetches GET /api/v1/projects/:id/rules/pass, and writes the result straight through the same parseRuleSet validator the engine trusts — so a response has to actually be valid v1 before it ever touches disk. Every write, rules.json and config.json alike, goes through a temp-file-then-rename so a killed process can't leave a half-written file.

All five paths covered by tests with a mocked fetch exercising the real request shape (URL, `x-api-key` header, JSON body) the live endpoint expects.

05Dashboard endpoint

GET /api/v1/projects/:id/rules/pass — read-only, reuses the existing authenticate() (no new auth system), returns the v1 envelope directly rather than the usual { data, meta } wrapper every other v1 route uses, because this response body is the file content prism pull writes verbatim.

The mapping logic lives in its own pure module (prism-rules-transform.ts) specifically so it's unit-testable without mocking Supabase/Next.js — 17 tests cover every branch above.

Not attempted: deriving required_token/arbitrary_value checks server-side from prism_brands token data. There's no foreign key from a project to a brand in the current schema, and adding one was explicitly out of scope ("Cosmos DB schemas or migrations beyond adding one read endpoint"). Local prism init is the only path that derives checks from real token data today; a project↔brand link is the natural follow-up once this ships.
