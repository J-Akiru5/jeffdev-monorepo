What needs your decision

The dashboard app today imports the CLI's rule engine in-process — not over a subprocess or network boundary — so an AGPL-3.0 license on the engine package puts the proprietary dashboard directly on the wrong side of the copyleft line the moment it ships. Separately, the repo is public with no per-app license marking, so the proprietary billing, tier, and admin code in apps/prism-engine is currently unmarked and defaults toward the root MIT grant rather than "all rights reserved."

  1. Coupling: decide whether Ox executes the arm's-length refactor (Section 1) before or in lockstep with flipping the license, and which boundary style — subprocess or HTTP.
  2. Exposure: decide between a two-repo split or single-repo per-directory licensing (Section 2) for the proprietary SaaS code.
01

Coupling audit

How apps/prism-engine actually consumes packages/prism-context-engine today, and what it would take to put daylight between them.

Current shape: in-process import, not a subprocess

Confirmed directly in the workspace graph and source. apps/prism-engine/package.json depends on @prism-engine/cli via workspace:*, and the CLI package exposes a second export target added in Phase 3:

FileExport
packages/prism-context-engine/package.json"./rules": "./dist/rules/index.js"

There is exactly one consumer of that subpath in the whole app, and it's a same-process function call, not a spawned process:

in-process apps/prism-engine/src/lib/sandbox.ts

import { parseRuleSet } from "@prism-engine/cli/rules" and import { checkContent, type Finding } from "@prism-engine/cli/rules" — both called synchronously inside runSandbox(), which parses a user-submitted rules.json and runs it against up to 20 sample files. This is the Phase 3 "sandbox preview" feature: it runs the exact parser/matcher the CLI hook uses, in the same Node process as the Next.js API route.

Every call site

There is only one production call site. It's exercised by one route and covered by one test file — the surface is small, which makes the refactor tractable.

Call siteWhat it's used for
src/lib/sandbox.ts → runSandbox() parseRuleSet() validates a submitted rules.json v1 envelope; checkContent() runs it line-by-line against sample files and returns findings (block/warn, rule id, message, offending snippet, suggested replacement).
src/app/api/v1/sandbox/run/route.ts Only caller of runSandbox(). Adds auth (authenticate()) and a strict per-user rate limit before invoking it — no AI calls, no quota burn, but user-supplied patterns still execute server-side.
src/lib/__tests__/sandbox.test.ts Unit tests against the in-process function directly.

Nowhere in apps/prism-engine does the app shell out to the prism binary as a subprocess. The rule engine's parser (parse.ts, 407 lines) and matcher (engine.ts, 410 lines) execute directly inside the dashboard's Node runtime via the barrel export in packages/prism-context-engine/src/rules/index.ts.

Proposed refactor: arm's-length invocation

Two viable boundary styles for the single call site. Both remove the in-process linkage; they differ in where the process boundary sits.

Option A

Subprocess call

MechanismRoute spawns the built prism CLI binary (already has a bin/prism.js entry) with rules.json and sample files piped in/out as JSON over stdio.
Latency+30–100ms typical for Node process spawn, on top of the existing sub-ms in-process call. Sandbox is already rate-limited "strict," so this is unlikely to be user-visible.
ComplexityLow-moderate. Needs a stable stdio contract (the CLI doesn't currently expose one for this), temp-file or stdin handling for up to 20 files, and process lifecycle/timeout handling in the route.
DeploymentRequires the CLI binary to be present and executable in the app's runtime image (Vercel/Node function) — a packaging change, not just a code change.
Option B

Thin HTTP boundary

MechanismRule engine runs as its own small service (or serverless function) with one endpoint; the dashboard route calls it over HTTP instead of importing the package.
Latency+network round-trip — single-digit ms in-region, more cross-region. Predictable, cacheable, easy to put a timeout on.
ComplexityHigher upfront: a service to deploy, own, and monitor; auth between the two now needs its own story (internal token or network policy) on top of the existing user auth.
DeploymentCleanest separation for licensing purposes — the AGPL code runs in a genuinely separate process the SaaS app talks to over a network API, which is the clearest reading of "arm's length" under AGPL's linking concerns.
Honest tradeoff: Option A is less work and ships faster, but "spawns a binary built from the same monorepo at the same commit" is a weaker separation than most conservative AGPL readings want. Option B is the safer legal posture but is real infrastructure work for what is currently a single low-traffic preview endpoint.

Effort estimate

  • Option A (subprocess): ~1–2 days — define the CLI's stdio contract, rewrite sandbox.ts to spawn + parse output, update the Dockerfile/build to ship the binary, adjust the test file to mock a process instead of a function.
  • Option B (HTTP): ~4–6 days — stand up the service (even as a minimal Fastify/Hono wrapper around parseRuleSet/checkContent), deploy pipeline, internal auth, route rewrite, timeout/retry handling, test updates.

This is a plan and estimate only. Whether Ox executes either option — and which one — is your call, not something to greenlight from this document.

Current licensing state

Confirmed by reading the actual files, not inferred:

  • Repo root has a single LICENSE file: MIT, copyright Syntaxure Labs. It applies to the whole tree with no directory-level carve-out.
  • packages/prism-context-engine has its own LICENSE (also MIT today — this is the package about to be relicensed to AGPL-3.0, and its own file hasn't been updated yet either).
  • apps/prism-engine has no LICENSE or NOTICE file of its own, and no per-file or per-directory license header anywhere in the directories listed above. As-is, a reader has no textual signal that this code is different from the MIT-licensed root — the honest reading is that the root MIT grant is the only license notice that applies to it.

This confirms the expectation going in: none of the proprietary code carries an explicit license or notice today.

Two options — real tradeoffs, no house recommendation

Option A

Split into two repos

StructurePublic engine repo (CLI + rule engine, AGPL-3.0) · private SaaS repo (dashboard, admin, billing, payments)
ExposureStrongest — nothing proprietary is ever in a public git history, including old commits and force-push residue.
CouplingForces Section 1's refactor to actually happen — a private repo can't import a public one in-process without vendoring, so the arm's-length boundary becomes structurally required, not just recommended.
Ongoing costTwo release cadences to keep in sync — a rule-engine schema or API change means a version bump published to the public repo, then a dependency bump in the private one before the SaaS app can use it. More CI, more coordination, more places for drift.
Option B

One repo, per-directory NOTICE

StructureStay monorepo. Add explicit LICENSE/NOTICE files inside apps/prism-engine (and any other proprietary app/package) marking it All Rights Reserved, distinct from the root grant.
ExposureLegal marking only — the code is still readable by anyone who clones the public repo, including full history. A NOTICE stops a licensing ambiguity claim; it does not stop a competitor from reading pricing logic or webhook handling.
CouplingDoesn't force Section 1's refactor — the in-process import keeps working, license notice or not. AGPL propagation risk from Section 1 is unresolved by this option alone.
Ongoing costCheaper to maintain day-to-day — one repo, one CI pipeline, no version-sync tax. Trades that for ongoing vigilance: every new file under a proprietary directory needs the header, and it's an easy thing to forget under deadline pressure with no CI check enforcing it unless one gets built.
Neither option is free. Option A pays continuously in coordination overhead; Option B pays continuously in exposure risk and requires someone to actually remember to keep the marking current. A hybrid — start with B now to close the immediate unmarked-code gap, move to A only if/when Section 1's refactor lands and gives you a clean seam to split at — is a sequencing choice, not a recommendation to pick B outright.
Investigation and proposal only. No LICENSE file added, no public claim made, no refactor executed. Secrets scanning out of scope — handled separately.
