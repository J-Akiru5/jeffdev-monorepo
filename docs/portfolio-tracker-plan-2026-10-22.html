Frame check — what you actually have vs. what you remember

The tracker “that we had” is not in the retired syntaxure-pm (that was a flat task board with no projects, clients, partners or retainers). The real predecessor is the prism-admin agency project detail: status, progress bar, client, start/deadline, budget, partner + employees, and milestones. Its app is paused and parts of it are broken (dropped columns, wrong insert shapes). So this work is a re-home + upgrade of that capability into prism-manage — the active ops tool per the repo’s own status notes — with the missing business concepts added properly.

Recommended architecture

1 · One source of truth: extend the existing projects table

The agency projects table is already the business-project record shared by the public site and the paused admin. Creating a second “portfolio projects” table would fork the truth and re-create exactly the drift we keep finding. Instead, add additive columns (no CHECK rewrites, no destructive changes) and new junction tables. The tracker then owns day-to-day portfolio management; the public site keeps reading published rows; the paused admin stays a CMS.

3 · Retainers — v1 depth

v1 keeps retainers as the four fields on projects plus a derived “maintenance” state. That covers status, monthly amount, and renewal date — enough to run the portfolio. Billing history and per-period invoices can come later by linking to the existing invoices/payments and client_contracts/contract_terms machinery; nothing in v1 blocks that path. (If you want the full ledger on day one, say so — it adds one table and roughly a phase of work.)

Header (name, kind, status, client, partners, live URL, published), progress control, retainer card (status, monthly, renewal), team (assignees + roles), milestones (add / complete / delete), linked task list with open-task counts, and the description/notes.

Contract-first, one owner per file set, sequential integration — parallel writes to the same app are how merge hell starts. I act as the integrator.

No deployment commands are run by agents; the eligible-branch integration handles deploys, and main promotion stays human-only (deployment-governance). Risks & sharp edges (from recon)

  • milestones table conflict — the original project-scoped definition and the workspace-scoped phase-6 definition collide. The tracker will use project_id milestones only. The prism-manage Operations milestones code queries workspace_id and may be silently broken — flagged for a separate verification, not fixed here.
  • prism-admin drift — its agency list reads a dropped client_name, and its “manage-projects” surface inserts columns that do not exist. Since prism-admin is paused, the tracker does not depend on it; note it for when that app resumes.
  • Two status fields — projects.status (site contract) and portfolio_status (tracker). Mapping is explicit and written by one action; no dual-write paths.
  • projects.user_id NOT NULL — seeded rows need an owner profile; the seed uses the earliest founder profile deterministically.
  • Public-site coupling — published projects appear at /work/[slug]; the tracker must never unpublish by accident when editing (publishing remains an explicit toggle).
