Prism CLI — Bearer-Session Authentication

Architecture decision + what changed + why · post-DOST-ASTI-demo work

1 · Executive summary

What shipped: the CLI's half-built Bearer/session auth path is now real and verified end-to-end against a live backend: prism login --token <token> → prism whoami → prism link → bare prism pull (no API key) → local enforcement. The API-key path (PRISM_API_KEY / x-api-key) is byte-for-byte untouched — the diff review confirms zero removed lines in that branch of api-auth.ts, and all pre-existing pull tests pass unchanged.

2 · The root cause (what was actually broken)

ClaimReality found in code
GET /api/auth/verify supports Authorization: Bearer Its own docstring says so, but the handler only called createClient() from @/lib/supabase/server — an SSR client bound to cookies. The header was never read. Every CLI verification failed regardless of token validity.
prism login authenticates the developer Stub: opens {apiUrl}/auth/cli — a route that did not exist (404) — then instructs prism login --token <token>, an option that wasn't registered. saveConfig({token}) was imported but never called; no code path ever wrote a token to ~/.prism/config.json.
Dashboard commands use the saved session projects list, api-keys, etc. send Authorization: Bearer via apiFetch — but the shared server authenticate() helper ignored the header too, so every v1 route rejected session calls (observed live: 401 Unauthorized).

3 · Architecture decision

3.1 One shared bearer path, three call sites

Rather than bolting header handling onto only the verify route, the fix lives in the one place every authenticated v1 route already shares — apps/prism-engine/src/lib/api-auth.ts — plus the verify route which reuses the same helper: 

authenticate(request)
 ├─ x-api-key header present        → sha256 hash → prism_api_keys lookup   [UNCHANGED, byte-identical]
 ├─ Authorization: Bearer <jwt>   → anon-key client → supabase.auth.getUser(jwt)   [NEW]
 └─ no header                       → cookie-bound SSR client (browser session)     [UNCHANGED]

The bearer branch resolves to a real Supabase user and returns source: "supabase" — the exact semantics of a browser session, so downstream behavior (RLS, created_by scoping in rules/validate) is identical. The JWT is validated by Supabase's auth server itself (getUser(jwt) overload); the anon key is a public client key, safe server-side.

3.2 CLI: session auth layered, API keys untouched

  • prism login --token <token> verifies via /api/auth/verify first, persists only on success into the existing global ~/.prism/config.json (config.ts schema unchanged). Browser mode now points at the real /auth/cli page.
  • prism pull auth resolution: PRISM_API_KEY env → .prism/config.json apiKey → global session token. Every failure mode keeps the exact fail-safe contract (warn + leave rules.json untouched + exit 0). --project <slug> works identically on both auth paths.
  • resolveProject() extracted from pull.ts into a shared, auth-agnostic helper (caller passes headers); prism link uses it with Bearer and persists into the existing .prism/config.json shape (activeProject + projects[slug] = {id}) — the same file a bare prism pull already reads.
  • prism whoami / prism logout — verify-and-print / clear the global token. Logout does not touch the API-key path by design (CI keeps working).

3.3 Tier gating (product decision)

Decision: the Bearer/login/link/pull path is free-tier accessible — it matches the existing free.apiKeys: 1 allowance ("exactly enough for CLI sync of the synced project") rather than connect's Pro-gated ideSync. Rationale: the same capability (rules sync) must not be priced differently by auth mechanism. /api/auth/verify still returns tier/ideSync in its payload, so a future Pro gate is a one-line change per call site.

Chain: dashboard rule → real sync → local enforcement — no fixtures, no mocks; the rule was created through the dashboard's own v1 API for the linked project.

6 · Guardrails honored

  • PRISM_API_KEY / x-api-key path untouched: git diff on api-auth.ts shows zero removed lines in the api-key branch; all pre-existing pull.test.ts cases (success/401/network/malformed/autopick/--project) pass unchanged.
  • prism pull --project <slug> still works identically on both auth paths (unit-tested; the shared resolver is auth-agnostic).
  • No schema changes: config.ts (global) and project-config.ts (local) shapes untouched; saveConfig({token}) reuses the existing merge-write.
  • Out of scope untouched: prism-admin, prism-manage, the rule engine, the dashboard, connect (its Pro gate remains as-is; its previously-dead Bearer flow now also works as a side effect of the shared fix — no code change there).
  • No new dependencies: engine already depends on @supabase/supabase-js; CLI additions use built-ins.

7 · Known limitations / follow-ups

  • /auth/cli is v1 copy-paste (no device flow); the token is intentionally rendered into the page HTML as the delivery mechanism — same trust model as any "copy your session token" flow.
  • The session token expires with the Supabase session (default 1h + refresh); a long-lived CLI token (e.g. refresh-token rotation or dedicated CLI tokens) is a future iteration — API keys remain the durable/CI credential.
  • All live verification ran against a local dev server; deploy requires the normal prism-engine build/promote, which was out of scope for this branch.
