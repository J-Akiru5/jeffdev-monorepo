H4 — Type Safety & Drift Guards

2026-10-19 Repo: jeffdev-monorepo Agent: opencode · DeepSeek V4.1 Flash (autonomous overnight) Branch: feat/pm-h4-type-safety → PR → develop Complete — CI green

Summary

The database now types the application. Generated schema types (pnpm db:types) flow into every Supabase client — server, browser, and service-role — and the whole app compiles against them: 27 type errors → 0. More importantly, the exercise found and fixed four real runtime bugs where code and schema had drifted apart (milestone creation could never succeed; BMC content writes were rejected; cost entries failed; a NULL page-parent query was wrong). A schema-drift guard now runs in CI, so this class of bug can't come back silently.

Real Bugs Found by Typing

HighMilestone creation was impossible (schema/code drift)
createMilestone() writes created_by (column never existed) and omits project_id / due_date — both NOT NULL in the live table. Every insert was rejected at runtime; nobody noticed because Operations is founder-only and rarely exercised.
Fix: migration 20261018000009 — added created_by, dropped NOT NULL from project_id and due_date (the app has no project concept for milestones and allows undated ones).
HighBMC block saves were rejected — content column was TEXT
The Business Model Canvas stores structured JSON per block, but bmc_sections.content was TEXT — PostgREST rejected every object write (save + seed).
Fix: same migration — column converted to JSONB (default swapped around the cast).
HighCost entries failed — created_by missing
Saving an infrastructure cost wrote created_by, which the Phase 6 table never had — every create was rejected.
Fix: migration 20261018000008 adds the column (provenance is genuinely useful for an ops cost tracker).
MediumNULL parent lookup used .eq() instead of .is()
Creating a top-level page queried parent_id=eq.null, which is invalid SQL semantics via PostgREST — sibling ordering fell back to 0.
Fix: the query now branches to .is("parent_id", null) for top-level pages.
MediumKPI updates were upserts that could not insert
updateKpi() used upsert({id, current_value}) — the insert arm violates NOT NULL on label/target_value whenever the row didn't exist.
Fix: it's an update of an existing KPI — now .update(...).eq("id", id).

The Drift Guard

CI (e2e job) → pnpm db:types:check
  → regenerates types from the LIVE schema
  → diffs against the committed file
  → fails with "Run `pnpm db:types` and commit the result."

Any migration applied without regenerating types — or any manual schema edit in Supabase — now surfaces as a red CI job instead of a runtime 400.
