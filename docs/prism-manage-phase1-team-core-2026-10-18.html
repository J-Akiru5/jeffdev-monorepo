Decisions & Checkpoints

Decision: zero RLS changes on tasks
Verified the existing policies already grant workspace members full access — the bug was purely app-code. Keeping the migration additive means prism-admin (which reads tasks/calendar_events/notifications) is unaffected, per the plan's pre-Phase-1 consumer check.
Judgment call: what happens to tasks when a list is deleted?
The FK is ON DELETE SET NULL, but orphaned tasks would vanish from the project-grouped UI. Instead, delete re-homes tasks to "General" first — and the General list itself can't be deleted.
Bonus fix: edit modals opened the wrong task
Discovered during recon: /api/tasks?id= was never honored, so every edit modal showed tasks[0] — the first task in the list, not the clicked one. Added getTask + id support; the existing page code already handled the single-object shape.
Deployment order: code vs migration
The new code writes pm_project_id, which only exists after the migration runs. Apply with supabase db push before pulling/using the new code — flagged in the PR and commit message. Not applied from this session (no DB access).
