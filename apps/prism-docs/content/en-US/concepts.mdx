# Concepts

Core concepts behind how Prism Context Engine works.

## What is MCP?

**MCP (Model Context Protocol)** is an open standard by Anthropic for connecting AI assistants to external tools and data sources. It uses JSON-RPC 2.0 over stdio (standard input/output).

When you configure Prism in your IDE's MCP settings, the IDE:
1. Launches `prism serve` as a child process on startup
2. Sends JSON-RPC requests over stdio (e.g., `get_architectural_rules`)
3. Prism responds with structured data the AI can understand

This means Prism is **not a cloud API** that your AI calls — it's a **local process** that your IDE talks to. Your rules never leave your machine during inference (they're embedded locally and the results are served locally).

---

## Rules vs Skills

Prism has two types of context:

### Rules — Always-On Governance

Rules are architectural constraints, style guides, and coding standards. They're included in every AI response (for relevant tasks).

**Examples:**
- "Always use Tailwind CSS classes, never inline styles"
- "Components must be in `/components/` with PascalCase filenames"
- "Use the `api.` wrapper for all HTTP calls, never raw `fetch`"

Rules are stored with a **priority** (1–100):
- Priority 1–3 = High → always returned with full content
- Priority 4–7 = Medium → returned if token budget allows
- Priority 8+ = Low → returned as a 2-sentence summary only

### Skills — On-Demand Procedures

Skills are step-by-step procedural guides. They're not loaded every time — only when the AI detects they're needed for the current task.

**Examples:**
- "How to create a new dashboard page"
- "Component creation checklist"
- "API endpoint setup procedure"

When AI calls `get_architectural_rules`, it gets:
- Full content for high-priority rules
- 1-line summaries for skills (name + what it does)

The AI then calls `get_skill(skillId)` separately to get the full procedure — only when it actually needs it. This is **progressive disclosure**.

## Smart Context Selection

Without Prism, your AI loads all rules every time — even rules unrelated to the task. This wastes tokens.

Prism uses **Gemini vector embeddings** to select only relevant rules:

1. Your AI calls `get_architectural_rules({ task: "build a login form" })`
2. Prism embeds the task string (3072-dimensional vector via `gemini-embedding-2`)
3. All your rules are also embedded (cached after first call)
4. Cosine similarity ranks rules by relevance to the task
5. Only rules above the threshold (0.72 similarity) are returned
6. Irrelevant rules are excluded

**Result:** "build a login form" returns auth/form/component rules, not testing or database rules.

**Token savings: ~30%** from this step alone.

---

## Progressive Disclosure

Even after smart selection, full rule content can be large. Progressive disclosure reduces this further:

**First response (light):**
```json
{
  "rules": [
    { "id": "...", "title": "Use Tailwind", "priority": "high", "content": "Full rule text..." }
  ],
  "skills": [
    { "id": "...", "name": "form-creation", "summary": "Step-by-step form building guide" }
  ],
  "tokenCount": 1840,
  "skippedRules": 24
}
```

Skills are metadata only (name + 1-line summary = ~40 tokens each). The AI sees them but doesn't get the full content yet.

**On demand (full skill):**
If the AI determines it needs the full form-creation procedure, it calls:
```
get_skill({ skillId: "form-creation" })
```

This fetches the full procedural guide only when needed.

**Token savings: ~20%** from progressive disclosure.

## Token Budget

Every `get_architectural_rules` call has a `maxTokens` budget (default: 4000).

Prism fills this budget intelligently:
1. High-priority rules first (always included, full content)
2. Medium-priority rules next (if budget allows)
3. Low-priority rules as 2-sentence summaries
4. Skills as metadata (30–50 tokens each)

The platform also enforces **IDE-specific caps**:
- Cursor: max 2,000 tokens per response
- Claude Desktop: max 1,500 tokens
- GitHub Copilot: max 1,000 tokens
- VS Code / Windsurf: uncapped (uses your requested budget)

---

## Caching

Prism has two cache layers:

### Response Cache (fastest)
If the same task + project + maxTokens combination is called again, the full response is returned from memory instantly — **0 Cosmos DB queries, 0 Gemini API calls**.

Cache key: `response_{projectId}_{task}_{maxTokens}_{format}_{category}_{tag}`
TTL: 30 minutes

### Rules Cache (fast)
DB query results for rules are cached. Only re-fetched if the rules have changed since the last sync.

**Token savings: ~10%** from cache hits (40%+ hit rate in practice means many calls are free).

## Active Enforcement

Prism doesn't just deliver context — it validates code and fixes violations:

### `prism_check`
Validates code against your rules that have regex `pattern` fields:

```
Input: generated TypeScript code
Output: { violations: [{ line, column, message, severity, suggestion }] }
```

In VS Code, this runs automatically when you save a file — violations appear as red/yellow underlines.

### `prism_fix`
Applies corrections for known violation patterns:

- Cross-app imports → `@repo/` alias
- Inline styles → Tailwind placeholder comment
- `console.log` → commented out
- Generic violations → appends `// FIXME: ruleName` comment

## Data Flow Summary

```
URL scan / repo scan
  ↓ Gemini extracts rules
  ↓ Saved to Cosmos DB

prism sync
  ↓ Rules downloaded to ~/.prism/rules.json

IDE opens project
  ↓ prism serve starts (spawns prism-mcp-server)

AI gets task
  ↓ get_architectural_rules({ task })
  ↓ Gemini embeds task → cosine similarity ranking
  ↓ Rules filtered, progressive disclosure applied
  ↓ Response cached (memory + disk)
  ↓ Telemetry logged

Developer saves file
  ↓ prism_check validates code
  ↓ Violations shown as diagnostics
  ↓ prism_fix applies quick-fix corrections
```
