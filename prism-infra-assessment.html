01

Problem Statement

The Azure trial/subscription backing Prism's database ran out of credit. Every code path that reads or writes Prism data calls a MongoDB client pointed at Azure Cosmos DB (MongoDB API). With that account suspended, those calls fail, and the product is effectively down.

⚠ Correction to the brief

The brief describes this as "Azure Container Apps + Cosmos DB." I found no Container App, Bicep/Terraform/ARM template, or any Azure compute reference anywhere in this repo. .github/workflows/deploy.yml deploys prism-engine, prism-admin, prism-manage, prism-docs, and prism-mcp-server to Vercel via amondnet/vercel-action. The Dockerfiles that exist per-app back local docker-compose.yml dev only — and even that compose file runs a plain mongo:7 image locally, not Cosmos or its emulator.

The only genuine Azure resources referenced anywhere in source or docs are Cosmos DB (Mongo API + Gremlin API) and an optional Azure OpenAI deployment used as one of three swappable LLM providers. That narrows the actual outage: compute is up and fine on Vercel — only the database account is dead. This is good news; it means fixing this is a data-layer problem, not a re-platforming problem.

02

Current Architecture Map

1Where Cosmos DB is used

There is a shared package — packages/db — but it only abstracts the connection, not the queries. It centralizes client construction and pooling; every call site still writes its own raw MongoDB query inline.

packages/db/src/cosmos.ts 
// Cosmos DB recommended settings
client = new MongoClient(MONGODB_URI, {
  retryWrites: false, // Cosmos DB doesn't support retryable writes
  maxPoolSize: 10,
  minPoolSize: 1,
  maxIdleTimeMS: 30000,
});

A representative call site — this pattern (import getCollection, run a raw query, inline in the handler) repeats 255 times across 64 files:

apps/prism-engine/src/lib/api-auth.ts 
import { getCollection } from "@syntaxure-labs/db/cosmos";

const apiKeysColl = await getCollection("apiKeys");
const record = await apiKeysColl.findOne({ keyHash: hash, revokedAt: null });
await apiKeysColl.updateOne({ _id: record._id }, { $set: { lastUsedAt: ... } });
LayerWhat it doesConsumers
packages/db/src/cosmos.tsMongoClient singleton, connection pooling, reconnect-on-stale logic64 files
packages/db/src/cosmos-gremlin.tsGremlin traversal source for the rules graph (tags / relates_to / conflicts_with)1 file, feature-flagged off

So: no repository or service layer sits between route handlers and the driver. packages/db answers "how do I get a connection," not "how do I fetch a project" — that logic is scattered call-site by call-site.

2Cosmos-specific features actually in use

I checked the live code paths for every Cosmos-only capability. Short version: none of them are actually in use. Prism treats Cosmos as a plain MongoDB-API document store.

FeatureIn use?Evidence
Native vector search NOT USED "Vector search" (lib/vector-search.ts) is plain JS cosineSimilarity() over embeddings pulled into memory — no $vectorSearch / Cosmos search index. Postgres+pgvector is a strict upgrade here (real ANN index vs. brute-force in Node).
Change feed NOT USED Zero references anywhere in the codebase.
Multi-region writes NOT USED No references in app code — would only exist as an account-level Azure setting, invisible to the app either way.
TTL indexes NOT USED No expireAfterSeconds index anywhere. The one "expiring" collection (governance_memory) filters expiresAt in application code and cleans up via a manual deleteMany() — already portable as-is.
Partition key strategy NOT USED No partition-key logic anywhere in application code. Whatever's configured lives purely at the Azure resource level.
Cosmos-only query syntax NOT USED Only standard Mongo CRUD + aggregation ($match/$group/$sum/$cond/$ifNull) — maps 1:1 to SQL GROUP BY / SUM / CASE / COALESCE.
Gremlin graph API USED, BUT DISABLED The one real non-relational feature: tag/relation/conflict edges boosting rule-ranking scores. Gated behind USE_GREMLIN_RANKING, default "false" — off in production today. No built-in Postgres equivalent, but the traversals are simple 1–2 hop edge lookups, cleanly replaceable with an edges table + recursive CTE.

What this means for migration difficulty: there's no interface to redirect — every one of the 255 call sites needs to actually change. But it's a mechanical change: .findOne() → prisma.x.findUnique(), .aggregate([$match,$group]) → groupBy() or raw SQL, repeated with minor variation. This is codemod-and-checklist work, not a redesign — the hard part is coverage (touching all 64 files), not conceptual difficulty.

04

Alternatives Comparison

Two real options, plus the do-nothing baseline for context.

Supabase — Postgres + pgvector Recommended
Same stack as every other app in this monorepo

Already true today

  • syntaxure-labs & syntaxure-pm already run on Supabase Postgres — 41 migrations, RLS policies, established patterns to copy
  • prism-engine's auth already migrated Clerk → Supabase (see MIGRATION_REPORT.md); @supabase/ssr and @syntaxure/supabase are already dependencies
  • packages/db already has Prisma + @prisma/adapter-pg wired for Postgres — just needs Prism's models added
  • Every Prism entity already has a Zod schema in packages/db/src/schema.ts — the data shapes are defined, not invented from scratch

Covers what Prism needs

  • Nothing in section 02 needs a feature Postgres/pgvector can't do
  • pgvector is an upgrade over the current in-app brute-force cosine similarity
  • Gremlin's disabled graph feature → small rule_edges table + recursive CTE, or skip it (it ships off today)

Real costs

  • ~14 collections need actual Prisma models + relations designed (schema exists as Zod, not as SQL)
  • 255 call sites across 64 files need rewriting — mechanical, not free
  • Mongo ObjectId → UUID touches 17 files
  • Existing Cosmos data needs export before the account is fully abandoned (or is accepted as disposable trial data)
Stay on Azure / swap to Atlas
Two sub-options, both zero-to-near-zero code change

Option A — refund the Azure subscription

  • Zero code changes, fastest possible unblock
  • Re-funds the exact failure mode that caused this outage
  • Second DB vendor + credential set outside the Supabase stack everything else uses
  • Doesn't touch the underlying "255 scattered raw queries" architecture problem

Option B — MongoDB Atlas (drop-in)

  • packages/db/cosmos.ts already wraps the plain mongodb npm driver — only the connection string changes
  • Free tier available; native Atlas Vector Search if embeddings ever need to move server-side
  • Still a second database platform bolted onto a monorepo consolidating on Supabase
  • Still doesn't fix the connection-only-abstraction / scattered-query pattern
05

Recommendation

Diagnosis complete → recommended path
Migrate to Supabase Postgres + pgvector, on a separate scoped pass.

Prism doesn't use anything Cosmos-specific in any live code path — no vector search, no change feed, no multi-region, no TTL indexes, no partition-key logic. Its one non-relational feature (Gremlin graph ranking) ships disabled by default. Meanwhile every sibling app in this monorepo, and Prism's own auth layer, already runs on Supabase with Prisma + the pg adapter wired and ready. This isn't a data-modeling problem or a "does the target support our use case" problem — it's a mechanical rewrite of ~255 query call sites, in a codebase that already has the target infrastructure half-built.

If the product needs to be back up today while the Postgres work is scoped properly: the fastest bridge is reactivating the Azure subscription, or re-pointing MONGODB_URI at a free-tier MongoDB Atlas cluster (near-zero code change, same driver, same query syntax). Either buys time without doing the real migration under outage pressure — it is a stopgap, not where Prism should end up.
